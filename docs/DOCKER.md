# Linux / Docker 一键部署

此方式独立于 Sites 运行：Node.js 24 生产服务、SQLite 数据库、本地附件存储、独立管理员登录、内置 SMTP 转接及 Caddy HTTPS。不是开发预览服务器。原 Sites 项目和线上数据不会被这些脚本修改。

## 首次部署

服务器需要已安装并运行的 Docker Engine、Docker Compose v2，以及 Git、Bash、flock。需要能下载 GitHub 源码、npm 依赖和 Docker 镜像。先把正式域名 DNS 指向服务器，并开放 TCP 80/443；避免与已有网站端口冲突。建议预留足够内存用于首次镜像构建。

```bash
git clone https://github.com/Yangdongle668/Screws.git
cd Screws
bash deploy.sh
```

按提示填写域名、管理员邮箱、至少14字符的后台密码、证书通知邮箱和允许的 SMTP 服务器域名。密码不回显、不写入命令参数；配置中只保存其 scrypt 散列。脚本生成独立会话密钥、邮件加密密钥和内部转接令牌，保存在权限为600的 `.env.docker`。不要提交或分享此文件。

首次构建和启动失败后可再次运行 `bash deploy.sh`，会保留已有配置继续尝试。部署成功后访问 `https://你的域名/admin/`，使用刚设置的账号登录。HTTPS 证书签发取决于 DNS、端口和证书服务可达性；容器健康不等于已验证外网证书。

这是新的独立数据库。原 Sites 的询盘、附件和后台发布文章不会自动出现在新服务器，正式切换前需单独安排数据迁移。仓库的基础页面和文章会随镜像提供。

## 后续一键更新

```bash
cd Screws
bash update.sh
```

更新顺序：检查本地修改与并发锁 → 拉取 `origin/main` 并仅允许快进合并 → 在旧服务运行时构建新镜像 → 停止唯一数据库写入进程并做完整备份 → 启动新版、运行事务化迁移及健康检查 → 记录新旧镜像版本。

- 构建失败不停止旧服务。备份失败中止更新，并尝试恢复旧服务。
- 源码有本地修改或分支不正确时停止，不执行强制覆盖。
- 备份与切换期间会有短暂停机，HTTPS 入口可能暂时返回502；这不是零停机部署。
- `data/` 和 `.env.docker` 不会在更新中被重建。更新不运行 `down -v` 或清理旧镜像。
- 若新版启动或迁移失败，保留旧镜像和更新前备份，并报告失败。不会自动覆盖数据库，因为这样可能丢失新记录，且旧程序不一定兼容新版结构。
- 代码更新不会替换已在后台发布的文章；这些内容仍保存在数据库中，必要时在后台单独编辑。

## 数据与备份

```bash
bash backup.sh
```

`backup.sh` 暂停网站写入后备份，并恢复服务；备份在 `backups/`。更新前也会执行同样的备份。定时备份尚未自动启用，可由管理员另设系统定时任务；不要与正在更新的操作重叠。

| 位置 | 内容 |
|---|---|
| `data/website.sqlite` 及 WAL 文件 | 询盘、备注、文章、统计、加密邮件配置 |
| `data/drawings/` | 客户图纸附件 |
| `data/smtp-receipts/` | 邮件去重及结果不明回执 |
| `.env.docker` | 密码散列、会话密钥、邮件加密密钥和运行配置 |
| `backups/` | 包含数据与敏感配置的完整停写快照 |
| `.deployment/` | 当前/前一镜像版本及操作锁 |

备份包含敏感信息，应加密离线保存，不能上传到公开仓库。请定期验证备份、安排异地副本和保留周期。删除数据目录、卷或邮件加密密钥可能导致数据或配置无法恢复。

恢复前先停止网站并另外保存当前数据。在独立临时目录检查选定备份，确认数据库、附件和 `.env.docker` 来自同一快照，再由管理员执行恢复；不要直接把旧快照覆盖正在接收询盘的数据库。恢复可能覆盖备份之后的新记录，因此脚本不自动执行破坏性恢复。

## SMTP 设置

后台“邮件通知”中填写 SMTP 域名、465 SSL/TLS 或587 STARTTLS、登录邮箱、密码、From和接收人。内部转接已自动配置，不用填写外部网关地址或令牌。证书验证始终启用。允许的 SMTP 服务器和发件域分别由 `.env.docker` 中 `SMTP_ALLOWED_HOSTS`、`SMTP_FROM_DOMAINS` 限定；变更后运行更新以重新加载配置。

先保存、诊断，再启用和测试实际收件。系统每分钟处理待通知邮件，询盘始终先入库。SMTP接受不等于进入收件箱，仍需配置实际邮件服务器及 SPF/DKIM/DMARC。发生结果不明的发送不盲目重发，需核对邮件服务器日志。

## 常用运维命令

```bash
docker compose --env-file .env.docker ps
docker compose --env-file .env.docker logs --tail=100 app https
```

脚本不记录请求正文、登录密码或 SMTP 密码。不要开启代理请求体或 Authorization 日志。网站容器不映射公网端口，仅通过 Caddy 访问；不要另外暴露3000端口、使用开发模式或信任外部传入的身份请求头。

`APP_VERSION` 是脚本设置的镜像标签。手工执行会重建容器的 Compose 命令前，应先执行 `export APP_VERSION="$(cat .deployment/current)"`，避免使用默认的 `local` 标签。查看日志和状态不需要设置。

## 统计与合规说明

访问统计仍遵循访客的可选统计同意。独立部署默认不配置 IP 国家数据库，国家显示 Unknown；不会把浏览器传入的国家请求头当成真实定位。需要地图定位时另行配置可信地理信息来源。主机/反向代理的日志保留与访问权限由服务器管理员负责。

Docker构建根据首次填写的域名生成 canonical、站点地图、结构化数据和 LLMS。更换域名后修改 `.env.docker` 的 `PUBLIC_URL` 和 `SITE_HOST`，更新DNS并重新运行更新；旧域名跳转、Search Console验证和正式收录监控仍需实际配置。

后台已发布文章保存的是发布时的HTML；更换域名后需复核并重新发布这些文章，使其规范网址和关联链接使用新域名。

## 验证范围

仓库的 GitHub Actions 包含 Docker 镜像构建及容器内测试：拒绝伪造身份、后台安全会话、同源检查、询盘幂等、附件与数据库重启持久化、备份，以及内置SMTP配置。测试不连接真实邮箱、不发送客户邮件。外网 DNS、HTTPS证书、真实邮箱和生产数据迁移仍须在目标服务器验收。
